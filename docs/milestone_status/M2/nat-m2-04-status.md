# NAT-M2-04 implementation status

Status: implemented and verified locally against the curated backend on 25 October 2026. Production authentication and a paired native/web walkthrough remain milestone integration work.

The Fleet Training screen now contains **Map / routes → Pre-trip routes**. Select a route, review its assigned shuttles, and either drag a graph node onto an interior graph node or type ordered numeric node IDs. Empty via input asks the backend to find a detour around active closures. M2 applies a route pattern to every assigned shuttle; unchecking an assignment blocks approval. The five screens continue to read committed routes and assignments from the single `TrainingWorkspace` session store.

`TrainingRouteContract.*` validates editor context and previews at the network boundary. `TrainingRouteClient.*` owns bounded REST requests, cancellation, validation dependencies, and pending route commands. `TrainingRouteEditor.*` displays the directed graph, committed route, static closure, draft path, canonical backend checks, stop coverage, and original/proposed metres, seconds, and estimated kWh. Unknown checks remain `UNKNOWN`; missing mandatory checks and inconsistent `approvable` flags are rejected. The editor shows backend speed, dwell, travel-energy and auxiliary-load assumptions instead of calculating route feasibility or energy in C++.

The new authenticated, read-only endpoint `GET /api/v2/sessions/{id}/routes/{route_id}/editor` supplies the curated graph and assumptions. Its model, generated schema, and shared fixture are in `contracts/v2/route_edit.py`, `route_editor_context.schema.json`, and `fixtures/route_editor_context.json`. Operational coordinates and metrics come from the committed map and `backend/fixtures/m2_route_detour.json`; the shared shape fixture is illustrative.

Approval requires a nonblank reason, all assigned shuttles, a `READY` session, and the exact freshly validated preview/draft revision. Draft edits, session/epoch changes, route/scene/transform/scenario changes, assignment changes, and closure revision or active-boundary changes invalidate review. Snapshot errors, event resync, joining, and a five-second snapshot-age limit disable decisions. Refresh can reload a failed graph request. Requests have a ten-second timeout, one outstanding request per kind, and a 512 KiB response limit; graph context is capped at 256 nodes/edges and previews at 128 edges.

The UI distinguishes pending submission, durable `QUEUED`, and authoritative `APPLIED`, `REJECTED`, `NEEDS_RECONFIRMATION`, or `EXPIRED` receipts, including failure code and effective tick. An applied receipt requests a new snapshot; it never directly replaces the active route. After an ambiguous reply or a `QUEUED` receipt, transport replays the identical approval POST, retaining its serialized body, command ID, idempotency key, and original session. This avoids treating an early command-status 404 as proof that a still-running approval did not apply, and lets the backend finish a queued approval. Retries back off from one second to a maximum thirty-second interval. A complete validation rejection on the initial POST releases the pending decision; errors on a replay remain inconclusive until a matching terminal receipt arrives. Read errors and session changes preserve the editor's pending lock. Late results from a different selected session are suppressed, while transport still releases the lock when that command settles. Mouse drags append new waypoints or replace an existing waypoint in place, preserving typed order and the sixteen-waypoint limit. Backend URL configuration and path joining are shared with `BackendClient`, including path prefixes and trailing slashes. All route drawing uses QWidget/QPainter on the Qt owner thread and creates no GL resources.

- All 48 selected backend/contract/store tests passed, including wrong-way travel, missing vehicle-fit metadata, stale revisions, simultaneous approvals, durable command recovery, and the authenticated graph endpoint. The new delayed-acceptance regression observes an unrecorded command while the original approval is in flight, replays that same request, and verifies both handlers return the same applied event with exactly one route revision change. - The separate real-backend integration test passed for both input methods.
