# M3: Persisted fleet training MVP

Task planning notes use the [dependency and blocker conventions](../milestones.md#task-dependencies-and-issue-creation). Dependencies name prerequisite artifacts; final paired evidence is a shared acceptance gate, not a reason to serialize client development.

3D extension (27 October 2026): existing tasks/handoffs remain unchanged. WEB-M3-07 through WEB-M3-09 and the additional exit criteria extend them under the [mandatory 3D contract](../three_d_simulation.md). Primary 3D is required from M2; 2D panels/minimaps and accessible fallback support but cannot replace it. New tasks remain planned until verified.

## Outcome and scope

A trainee can prepare a shift against timed disruptions, handle concurrent incidents, maintain charging coverage and return to a persisted debrief. A trainer can create and publish a constrained scenario using the application.

The MVP supports the approved pre-trip and in-trip training workflow across web and native. Its robustness includes conflict handling, reconnect recovery, understandable validation and reproducible exports.

Dependencies: [web M2](m2.md), [backend M3](../backend/m3.md), [native M3](../native/m3.md), published revision contracts and P1 acceptance fixtures.

## Tasks

### WEB-M3-01: Timed route constraints and iterative editing

**Dependencies:** [WEB-M2-03](m2.md#web-m2-03-pre-trip-route-preparation), [BE-M3-01](../backend/m3.md#be-m3-01-complete-pre-trip-planning-and-validation).

**Required inputs:** BE-M3-02 branch contract and explicit timezone/boundary semantics.

**Planned blockers / completion gates:** Requires stale-response rejection and server validation of polygons/timed constraints; simulate-before-approve must use an isolated branch and fresh live revalidation.

- Add segment closure windows with explicit timezone and inclusive/exclusive boundary semantics supplied by the contract.
- Add avoid-area polygon editing, vertex handles, self-intersection feedback and an accessible coordinate/list alternative.
- Show affected route/time combinations, stop relocation or skipped-stop consequences and constraint provenance.
- Request suggested detours with bounded candidate counts, reject reasons and comparison metrics.
- Cancel obsolete preview requests and use draft revision tokens so slower replies cannot restore an old route.
- Keep undo/redo local to the draft; a previously approved route remains immutable and must be cloned to edit.
- Support simulate-before-approve in an explicitly separate preview branch, then revalidate against the current live session before commit.

Output: timed-closure and accessible avoid-area editors, revision-safe detour requests/comparison, local draft history, and isolated simulate-before-approve flow.

Verification: boundary times, self-intersecting polygons, stop changes, and no-route fixtures show actionable results; reordered responses cannot restore an obsolete draft, and branch inspection leaves the live session unchanged before fresh approval validation.

### WEB-M3-02: Route deployment and shared-session conflicts

**Dependencies:** [WEB-M2-02](m2.md#web-m2-02-authoritative-command-and-stream-foundation), [WEB-M3-01](m3.md#web-m3-01-timed-route-constraints-and-iterative-editing), [BE-M3-01](../backend/m3.md#be-m3-01-complete-pre-trip-planning-and-validation).

**Required inputs:** Atomic target-set deployment and safe activation contracts.

**Planned blockers / completion gates:** Partial client approval, lost ledger entries after panel closure or silent conflict merges block completion; paired native approvals provide acceptance evidence.

- Present which shuttles receive a route and the backend-defined effective tick or safe activation point.
- Present one atomic queued/applied/rejected deployment result for the requested shuttle set, with per-target rejection explanations.
- Do not present partial approval when one target has changed; show any subsequent vehicle execution issue as a separate event.
- Handle another actor's edit with a revision comparison and a deliberate refresh/rebase flow; never silently merge approvals.
- Bind any approval to the validated draft, graph/disruption versions, expected assignments and recorded reason.
- Keep issued commands in the shared ledger even if the originating panel closes.

Output: explicit target-set route deployment, effective-time/revision display, persistent command ledger, and deliberate conflict refresh/rebase UI.

Verification: simultaneous web/native edits yield one backend-authoritative atomic deployment, never a client-invented partial success; closing the issuing panel does not lose command status, and changed targets/constraints require renewed review with the user's reason preserved.

### WEB-M3-03: Concurrent incident triage and replay

**Dependencies:** [WEB-M2-04](m2.md#web-m2-04-fleet-overview-and-bounded-incident-response), [BE-M3-02](../backend/m3.md#be-m3-02-complete-in-trip-decision-management).

**Required inputs:** Paged immutable evidence and per-incident command/expiry contracts.

**Planned blockers / completion gates:** Must keep live alerts and independent review cursors during concurrent decisions; expired/peer-resolved options cannot remain actionable.

- Implement sortable/filterable incident queues with severity, affected shuttle, elapsed decision time and freshness.
- Preserve a selected incident while other fleet updates arrive; announce new critical incidents without stealing focus.
- Present backend explanation evidence and candidate constraints in plain language, including unknown or stale evidence.
- Support wait expiry, escalation status, road detour and manual road-network reroute with server validation.
- Load historical ranges on demand and anchor them to event sequence/tick rather than client arrival time.
- Maintain independent live, history and branch cursors, with an explicit return-to-live action and continued live incident notifications.
- Display candidate invalidation when another decision, closure or vehicle movement makes a preview stale.

Output: stable concurrent-incident queue, manual detour/wait/escalation controls, paged evidence history, and independent live/history/branch cursors.

Verification: peer resolution and candidate expiry invalidate stale choices; new critical incidents remain visible without stealing focus, wait expiry/escalation follow server state, and historical inspection cannot pause the live fleet or submit a decision against historical state.

### WEB-M3-04: Charge scheduling and swaps

**Dependencies:** [WEB-M2-05](m2.md#web-m2-05-battery-choice-and-simple-debrief), [BE-M3-03](../backend/m3.md#be-m3-03-implement-battery-and-charging-operations).

**Required inputs:** Accessible time/interval inputs and structured reserve/coverage/depot constraints.

**Planned blockers / completion gates:** Needs atomic booking/swap APIs and conflict fixtures; rejected/timeout proposals must retain the last confirmed schedule without fake reservations.

- Build the fleet/charger timeline with service, standby, charging, proposed and unavailable intervals.
- Edit a proposed booking or swap through accessible forms and optional drag interactions.
- Show reserve, depot reachability, charger conflicts and minimum service coverage before approval.
- Compare feasible alternatives using backend duration/energy/coverage estimates and explanatory rejection reasons.
- Mark scheduler timeout, no feasible plan and stale-plan responses distinctly; retain the last confirmed schedule.
- Submit an atomic schedule/swap command with expected plan revision and show all dependent reservation outcomes.
- Reconcile another client's bookings and conflicts without locally pretending a charger is available.

Output: accessible fleet/charger timeline, booking/swap proposal forms, constraint and alternative comparison, and atomic approval/reconciliation flow.

Verification: charger overlap, maintenance, unreachable depot, reserve, and service-coverage fixtures produce the backend's accepted/rejected outcomes; timeout or stale plans retain the confirmed schedule, and competing clients cannot display two successful reservations for one exclusive slot.

### WEB-M3-05: Minimum trainer authoring and persistent debrief

**Dependencies:** [WEB-M2-01](m2.md#web-m2-01-typed-feature-shell-and-common-interaction-language), [WEB-M2-05](m2.md#web-m2-05-battery-choice-and-simple-debrief), [BE-M3-04](../backend/m3.md#be-m3-04-add-minimum-trainer-authoring-and-assignment), [BE-M3-05](../backend/m3.md#be-m3-05-persist-debrief-score-explanations-and-exports).

**Required inputs:** Trainer/trainee access and immutable scenario/report identity.

**Planned blockers / completion gates:** Cannot close until publication, restored debrief and backend report downloads work with protected references excluded from trainee payloads.

- Add role-gated scenario clone/edit forms for route assignments, closures, incident trigger, battery/charger setup and seed.
- Provide a constrained reference response and rubric configuration with validation messages from the backend.
- Require validation before publish; display immutable published revision and create a new draft for subsequent changes.
- Keep reference answers unavailable to trainees until the configured debrief stage; the backend must withhold them from ordinary session payloads.
- Restore sessions and saved debriefs through server history, including command reasons, attempts, response time and route/charge consequences.
- Display score dimensions and rubric version; explain unknown/missing dimensions rather than substituting zero.
- Download backend-generated JSON/CSV and a human-readable report with session/scenario identity and provenance.

Output: role-aware scenario authoring/publication, immutable revision display, restored debrief/score explanations, and backend-generated JSON/CSV/human-readable downloads.

Verification: invalid drafts cannot publish and editing cannot change an active attempt; trainee payloads do not expose protected reference answers, and restored scores and exports match committed session/scenario/rubric evidence with unavailable dimensions clearly identified.

### WEB-M3-06: MVP performance and recovery

**Dependencies:** [WEB-M2-02](m2.md#web-m2-02-authoritative-command-and-stream-foundation), [WEB-M2-06](m2.md#web-m2-06-rendering-alerts-and-measurement-foundation).

**Required inputs:** BE-M3-06 replay/queue contracts and fixed P1 setup.

**Planned blockers / completion gates:** Recovery/cache work can proceed early; final passing P1 requires WEB-M3-01/02/03/04/05 plus 3D editing/review/depot workloads. No unbounded background-tab catch-up.

- Extend the M2 transport worker for expensive history preparation where profiling demonstrates contention.
- Use small selector subscriptions, batched notification and replaceable snapshot slots to keep fleet motion out of general React rerenders.
- Cache scene assets by immutable revision and bound route/history caches; evict obsolete branch resources.
- Recover via durable event cursor plus a verified state baseline; expose reset when the server's retention window has expired.
- Add foreground visibility handling so background tabs do not accumulate an unbounded processing backlog.
- Meet P1 command acceptance, applied-visible, state-age, and route-validation and rendering gates from [performance.md](../performance.md).

Output: bounded worker/store/cache pipeline, durable-cursor recovery, background-tab handling, and complete-workflow P1 benchmark results.

Verification: baseline/event-history loss triggers a consistent resync rather than silent state loss; foreground return cannot replay an unbounded backlog or duplicate effects, and all mandatory P1 gates pass during the complete paired-client MVP workflow.

### WEB-M3-07: Complete surface-aware 3D authoring

**Dependencies:** [WEB-M2-08](m2.md#web-m2-08-navigate-and-edit-the-3d-training-scene), [WEB-M3-01](m3.md#web-m3-01-timed-route-constraints-and-iterative-editing), [WEB-M3-05](m3.md#web-m3-05-minimum-trainer-authoring-and-persistent-debrief), [BE-M3-07](../backend/m3.md#be-m3-07-validate-surface-aware-routes-and-volume-clearance), [BE-M3-08](../backend/m3.md#be-m3-08-add-revisioned-3d-scenario-placement-and-depot-semantics).

**Required inputs:** Stacked-deck/headroom fixtures and keyboard placement controls.

**Planned blockers / completion gates:** Exact surface selection and authoritative placement validation are prerequisites to approval; ghost geometry cannot become committed state locally.

- Extend route/avoid-area editing with explicit surface/deck selection and depth-aware polygon/waypoint handles.
- Add trainer obstacle placement, orientation and dimension forms with a ghost preview tied to a validated scenario draft or authorised intervention.
- Locate support/headroom/body-envelope failures in the 3D world and equivalent text; do not silently snap ambiguous hits to another road level.
- Preserve revisions, reason text and undo/cancel while camera movement, async validation and peer edits occur.

Output: 3D route/area/trainer-placement controls, surface disambiguation, validation overlays and keyboard alternatives.

Verification: stacked roads and low-headroom fixtures produce exact feature IDs and backend decisions; invalid/stale placement never becomes authoritative local geometry, and keyboard and pointer submissions remain semantically equivalent.

### WEB-M3-08: Review 3D history, branches and synthetic cameras

**Dependencies:** [WEB-M2-09](m2.md#web-m2-09-render-authoritative-3d-execution-and-measure-it), [WEB-M3-03](m3.md#web-m3-03-concurrent-incident-triage-and-replay), [BE-M3-09](../backend/m3.md#be-m3-09-persist-and-replay-the-complete-3d-state).

**Required inputs:** Immutable scene lineage and live-plus-one-review viewport budget.

**Planned blockers / completion gates:** Replay/asset cancellation and source boundaries must hold across branch changes; synthetic onboard views remain labelled and cannot reuse unrelated recordings.

- Bind historical/preview worlds to their exact scene/assets and authoritative pose ticks, with independent camera/cursor/transform state.
- Add a persistently labelled SIMULATED VIEW onboard camera; source recording remains a separately identified evidence item.
- Keep main live plus one review/onboard inset within the two-viewport budget, sharing only immutable assets and suspending unused views.
- Cancel obsolete history/asset jobs and reclaim branch render targets when views close; preserve live incident notifications.

Output: isolated 3D review/preview store, synthetic onboard view, bounded viewport manager and source/scene lineage fixtures.

Verification: scrubbing never changes live state or replays old alerts, same-tick poses match saved evidence, and a branch cannot continue unrelated KITTI footage or upload stale geometry into the current session.

### WEB-M3-09: Complete 3D charging execution and P1 acceptance

**Dependencies:** [WEB-M3-04](m3.md#web-m3-04-charge-scheduling-and-swaps), [WEB-M3-07](m3.md#web-m3-07-complete-surface-aware-3d-authoring), [WEB-M3-08](m3.md#web-m3-08-review-3d-history-branches-and-synthetic-cameras), [BE-M3-03](../backend/m3.md#be-m3-03-implement-battery-and-charging-operations), [BE-M3-08](../backend/m3.md#be-m3-08-add-revisioned-3d-scenario-placement-and-depot-semantics).

**Required inputs:** WEB-M3-06 instrumentation and paired native 3D runtime.

**Planned blockers / completion gates:** Completion needs visible supported approach/arrival/charge/swap execution and full 3D P1/spatial evidence, with no teleportation or reservation-driven fake occupancy.

- Link charger/depot timeline selections to dimensioned bays, shuttle poses and backend-approved approach/return routes.
- Show proposed reservations as ghosts and committed arrival/dwell/charge/swap transitions as authoritative state; animation grants no occupancy.
- Run full 3D training, trainer placement and review with both real clients under the frozen scene/camera workload.
- Capture timing, resource and spatial results together, including viewport/content/quality identities.

Output: scene-integrated charging workflow, complete 3D MVP script and mandatory P1/spatial parity report.

Verification: competing reservations cannot show two occupants of an exclusive bay, vehicles do not teleport to a schedule location, and the complete 3D workload passes P1 while matching native/backend outcomes and geometry.

## Additional 3D exit criteria

- The complete training/authoring MVP uses 3D route/placement, incident, depot and replay workflows with explicit surface/scene identity.
- Synthetic camera/source boundaries, multi-level picks and headroom/fit rejection agree with backend/native.
- All mandatory P1 gates pass with the primary 3D scene and required inset loaded; existing form-only tests are necessary but insufficient.

## Verification and failure cases

- Exercise timed closure boundaries, self-intersecting polygons, disconnected detours, moved stops and no-feasible-route responses.
- Simultaneously approve conflicting web/native route changes and charger reservations; both clients converge to the same result.
- Disconnect during approval, restart the client and reconcile the original idempotency key without duplicate effects.
- Drop a snapshot baseline and interrupt the durable event stream; verify correct recovery rather than silent interpolation.
- Expire a candidate while its comparison view is open; submission must be rejected or revalidated clearly.
- Inspect history while new incidents arrive and verify that live state, local inspection and live alert delivery remain independent.
- Confirm score/report values match stored backend outcomes after session restoration.
- Complete the full workflow using keyboard navigation and a screen reader's form/list navigation.

## Deliverables and exit evidence

- Full MVP route/incident/charging/debrief workflows and minimum trainer authoring.
- Repeatable end-to-end scenarios for route closure, concurrent incidents, low battery, charger conflict and restart recovery.
- P1 percentile traces from paired web/native runs, with cache state, hardware and network conditions recorded.
- Contract and conflict fixtures shared with native; no client-specific meaning for a status or score field.
- Persisted sample reports with session, scenario, graph, rubric and command provenance.
- Documented known limitations and supported browser/viewport matrix.

M3 exits when a trainer can publish an exercise and a trainee can complete, recover and review it entirely through the application, with P1 gates demonstrated.
