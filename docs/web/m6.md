# M6: Validated beta and handover

Task planning notes use the [dependency and blocker conventions](../milestones.md#task-dependencies-and-issue-creation). Dependencies name prerequisite artifacts; final paired evidence is a shared acceptance gate, not a reason to serialize client development.

3D extension (27 October 2026): existing tasks/handoffs remain unchanged. WEB-M6-07 through WEB-M6-09 and the additional exit criteria extend them under the [mandatory 3D contract](../three_d_simulation.md). Primary 3D is required from M2; 2D panels/minimaps and accessible fallback support but cannot replace it. New tasks remain planned until verified.

## Outcome and scope

Release a frozen, reproducible beta of the fleet manager training application with user-observed workflow evidence, transparent performance results and an understandable handover.

M6 validates and packages the M5 feature set. New features require explicit scope decisions and cannot silently displace acceptance, reliability or user evaluation.

Dependencies: [web M5](m5.md), [backend M6](../backend/m6.md), [native M6](../native/m6.md), frozen scenarios/rubrics and the integrated acceptance checklist.

## Tasks

### WEB-M6-01: Freeze and candidate reproducibility

**Dependencies:** [WEB-M5-01](m5.md#web-m5-01-feature-completion-and-contract-freeze), [WEB-M5-06](m5.md#web-m5-06-release-diagnostics-and-build-discipline), [WEB-M5-09](m5.md#web-m5-09-close-spatial-and-3d-interaction-regressions).

**Required inputs:** Accepted M5 gates, matching backend candidate and frozen browser/hardware/fixture inventory.

**Planned blockers / completion gates:** Clean build, compatible cache behavior and optional-feature dispositions are required; every release fix needs recorded affected regression checks.

- Tag the candidate source, lock dependencies and record frontend/backend/schema compatibility.
- Freeze training fixtures, graph/scenario/rubric revisions, browser versions and benchmark machine information.
- Verify a clean install and production build from the documented steps.
- Confirm cached clients detect incompatible deployments and offer a clear reload/recovery path.
- Maintain a narrowly scoped beta defect branch with a record of changes and affected regression checks.
- Keep unresolved optional capabilities disabled instead of presenting placeholders as delivered functionality.

Output: frozen candidate/dependency/compatibility manifest, fixed scenario/benchmark environment, clean-build instructions, and scoped defect/regression log.

Verification: a clean environment reproduces the production candidate using the documented inputs; cached incompatible clients receive a safe reload/recovery path, optional unfinished capabilities remain disabled, and each candidate fix records its affected regression checks.

### WEB-M6-02: Observed trainee and trainer validation

**Dependencies:** [WEB-M6-01](m6.md#web-m6-01-freeze-and-candidate-reproducibility).

**Required inputs:** Working frozen exercise, trainer/trainee script, participants and consented aliases.

**Planned blockers / completion gates:** Blocking comprehension/recovery failures must be corrected and retested; participant limitations must be recorded rather than inferred as professional efficacy.

- Prepare tasks covering pre-trip disruption editing, validation/approval, incident triage, charge/swap choice and debrief interpretation.
- Ask participants to complete the tasks without developer assistance and record completion, errors, hesitation and recovery.
- Include at least one trainer authoring/review task and one interrupted-session recovery task.
- Measure whether users understand predicted versus actual outcomes, expired candidates and the recorded/simulated boundary.
- Check whether users can explain the reason for a rejected route or schedule from the UI.
- Use consented participant aliases and record recruitment limitations; proxies do not prove professional training efficacy.
- Turn observed issues into reproducible defects, prioritising incorrect actions, misunderstandings and inability to recover.

Output: consented trainee/trainer observation records, task-completion/error/comprehension results, participant limitations, and prioritised reproducible usability defects.

Verification: the agreed study script covers all core decisions, authoring/review, and interrupted-session recovery; findings distinguish observed performance from professional-efficacy claims, and blocking misunderstandings or failed recovery paths are corrected and retested before acceptance.

### WEB-M6-03: Frozen cross-client acceptance

**Dependencies:** [WEB-M6-01](m6.md#web-m6-01-freeze-and-candidate-reproducibility).

**Required inputs:** Matching backend/native packages, frozen seed/revision scripts and supported browser matrix.

**Planned blockers / completion gates:** Final paired/independent runs must agree on decisions, reports, permissions and provenance on the actual candidate; earlier demo builds do not close acceptance.

- Execute the same scenario/seed/revision scripts in web and native, including a paired-client session.
- Compare final route assignments, incident outcomes, charge reservations, decision reasons and score/report values.
- Verify role restrictions and conflict handling with different authorised actors.
- Confirm source labels and historical/branch boundaries match across both clients.
- Test each supported browser and required viewport/theme combination.
- Capture accepted evidence against the exact release candidate, not an earlier demonstration build.

Output: frozen-build cross-client acceptance matrix with run/seed/revision identities, conflict/permission results, and supported browser/viewport/theme evidence.

Verification: independent and paired runs agree on authoritative route, incident, charging, reason, score/report, and source-boundary semantics; every required supported configuration passes, and the evidence identifies the actual released candidate.

### WEB-M6-04: Final latency and resilience evidence

**Dependencies:** [WEB-M6-01](m6.md#web-m6-01-freeze-and-candidate-reproducibility), [WEB-M5-02](m5.md#web-m5-02-foreground-performance-and-load), [WEB-M5-03](m5.md#web-m5-03-endurance-and-resource-lifecycle), [WEB-M5-04](m5.md#web-m5-04-network-and-concurrency-resilience).

**Required inputs:** Final backend/native packages, canonical measurement setup and working complete workflows.

**Planned blockers / completion gates:** Requires raw final P1/P2 and four-hour soak/recovery evidence; missed mandatory budgets or duplicate command effects block release. Include WEB-M6-07/08 spatial workload.

- Rerun P1 acceptance and the agreed P2/endurance matrix from [performance.md](../performance.md).
- Record command acceptance separately from command application and first visible authoritative state.
- Report frame-time and state-age tails, reconnect time, route/candidate latency and resource bounds.
- Include warm/cold asset status, network conditions, hardware, sample counts and any excluded measurements.
- Rehearse a backend restart, a lost command acknowledgement and a client refresh during an exercise.
- Explain failed targets and remaining limits candidly; do not relabel a target as achieved without a trace.

Output: final P1/P2 measurement report, four-hour frozen-build soak, recovery fault traces, raw sample metadata, and measured supported-load/limitation statement.

Verification: mandatory P1 and P2 correctness/recovery/resource gates pass with the canonical timing definitions; the four-hour soak meets bounded-resource/plateau criteria, restart and lost-acknowledgement cases preserve one durable outcome, and indicative P2 speed misses or exclusions are disclosed rather than counted as passes.

### WEB-M6-05: User documentation and operational handover

**Dependencies:** [WEB-M6-01](m6.md#web-m6-01-freeze-and-candidate-reproducibility).

**Required inputs:** Backend startup/role/recovery contracts and frozen user interaction behavior.

**Planned blockers / completion gates:** Guides can be drafted early; final handover needs verified publish-to-debrief and recovery steps plus findings from WEB-M6-02/09, with no hidden developer dependencies.

- Provide a short trainer guide for scenario publication, role assignment, reference solutions and interpreting score dimensions.
- Provide a trainee guide covering route preparation, incident choices, charging trade-offs and debrief review.
- Explain training assumptions, model limits, estimates and the purpose of recorded versus simulated material in plain language.
- Document startup, account/role configuration where applicable, data reset/backup and report export.
- Include troubleshooting for stale state, reconnect, unavailable assets, validation conflicts and unsupported capabilities.
- Provide a keyboard interaction reference and theme/audio/reduced-motion settings.

Output: trainer/trainee guides, model/source-limit explanations, startup and data/recovery instructions, keyboard reference, and troubleshooting/settings guidance.

Verification: a reviewer can complete the documented publish-to-debrief workflow and a supported recovery using only the guides; roles, source boundaries, export steps, and backup/reset warnings match the frozen product without hidden developer-tool dependencies.

### WEB-M6-06: Release and demonstration package

**Dependencies:** [WEB-M6-01](m6.md#web-m6-01-freeze-and-candidate-reproducibility).

**Required inputs:** Versioned example scenarios/reports and compatible backend/native deployment configuration.

**Planned blockers / completion gates:** Prepare artifacts early; publish final handover only with WEB-M6-02/03/04/05 and WEB-M6-07/08/09 evidence, closed blockers and same-build live/fallback demonstrations.

- Package the production web build with deployment configuration and a matching backend/native compatibility manifest.
- Ship versioned example scenarios and representative reports without unnecessary personal data.
- Prepare a timed demonstration that begins with a route disruption and ends with evidence in the debrief.
- Include a deliberate failure/recovery segment so robustness is demonstrated directly.
- Record a fallback demonstration using the same frozen build and fixtures.
- Publish the final known issues, ownership/handover notes and the measured supported load envelope.

Output: versioned production web package, deployment/compatibility manifest, example scenarios/reports, timed live and fallback demonstrations, and owner-assigned handover/known-issue records.

Verification: packaged configuration starts the compatible release and reproduces the route-to-debrief demonstration including deliberate recovery; example reports match their frozen scenarios, recordings use the same candidate, and artifacts contain no unnecessary personal data, misleading placeholders, or unsupported load claims.

### WEB-M6-07: Package and deploy the complete 3D world

**Dependencies:** [WEB-M6-01](m6.md#web-m6-01-freeze-and-candidate-reproducibility), [WEB-M5-08](m5.md#web-m5-08-harden-3d-asset-and-context-lifecycle), [BE-M6-07](../backend/m6.md#be-m6-07-ship-reproducible-3d-scene-and-model-packages).

**Required inputs:** Production loader/shaders, immutable cache policy and retained content inventory.

**Planned blockers / completion gates:** Clean and cached deployment must load the pinned world offline; incompatible or missing mandatory assets cannot silently become a passing flat view.

- Ship the production loader/profile dependencies, mandatory assets, material/shader settings and scene/spatial checksums with the compatible backend/native manifest.
- Verify local deployment without runtime internet content downloads and define immutable asset cache/version invalidation.
- Distinguish unsupported graphics/profile and missing mandatory geometry from optional detail loss; preserve useful diagnostic/recovery guidance.
- Retain content required by saved attempts and demonstrate both cold and cached scene readiness.

Output: versioned 3D web/content release bundle, cache/compatibility manifest and clean-environment readiness evidence.

Verification: the released app loads the correct dimensioned world from packaged requirements, cached incompatible assets cannot reinterpret a scene, and missing required content cannot silently fall back to a passing flat view.

- Execute AT-13 through AT-18 at applicable scope using the packaged clients/backend and exact scene/camera script.

Verification: mandatory spatial, performance and resource gates pass with actual 3D rendering; recovery retains correct geometry, provenance and commands, while optional local passing/perception follow their separate acceptance rules.

### WEB-M6-09: Validate and hand over 3D usability

**Dependencies:** [WEB-M6-07](m6.md#web-m6-07-package-and-deploy-the-complete-3d-world).

**Required inputs:** Observed 3D task script, participants, keyboard/screen-reader and DPI/theme matrix.

**Planned blockers / completion gates:** Final sign-off needs corrected/retested navigation, road-level selection, ghost/applied and synthetic/recorded comprehension; feed findings into WEB-M6-05/06 guides and demo.

- Observe users selecting shuttles/road levels, navigating cameras, editing 3D routes/obstacles and interpreting blocked-space evidence.
- Test synthetic onboard versus recorded evidence comprehension and pending/ghost versus applied object state.
- Include keyboard, screen-reader summaries, supported DPI/themes and recovery from graphics unavailability; fix and retest blockers.
- Extend guides/demo/known limits with camera/edit controls, scene readiness, quality settings and simplified model assumptions, referencing the new task evidence.

Output: 3D usability/accessibility observations, retest results and updated trainee/trainer/support handover.

Verification: observed tasks support the released interaction/source claims, documentation reproduces the 3D demonstration and a supported recovery, and no unmeasured fidelity/capacity claim or erased earlier handoff is required.

## Additional 3D exit criteria

- Clean-machine and cached deployment reproduce the mandatory 3D experience with the released scene/assets and backend/native compatibility.
- Final spatial parity, P1 and four-hour 3D endurance/recovery pass without flat/minimized-renderer substitution.
- Observed 3D interaction/accessibility and supporting guides are complete; unresolved mandatory 3D failures block release.

## Verification and failure cases

- Install from a clean environment using only the release guide and packaged requirements.
- Complete every core scenario after clearing browser cache and again with cached assets.
- Confirm report files match visible results and include scenario/session/rubric provenance.
- Verify a disconnected trainee cannot mistake an old state or queued action for a new successful decision.
- Repeat tests affected by usability fixes; any contract or simulation change requires the corresponding paired-client regression.
- Check release artifacts for debug controls, placeholder scores, unlabelled estimates and misleading sample data.
- Confirm optional perception and curated manoeuvre features remain capability-gated in the packaged build.

## Deliverables and exit evidence

- Versioned web beta artifact, build instructions and compatibility manifest.
- Completed acceptance matrix linking each core workflow to test/demo evidence.
- Usability findings, observed task outcomes, fixes and clearly stated participant limitations.
- Final percentile performance/resilience report with raw evidence and unresolved limits.
- Trainer/trainee guides, troubleshooting instructions and known issues.
- Demonstration recording and sample reports from the frozen candidate.

M6 exits when the release can be reproduced, the complete training workflow is accepted in both clients, and user/performance evidence supports the claims made in the final presentation.
