## BE-M2-01: Define the training domain and versioned contracts

**Dependencies:** No earlier task; establish the shared foundation.

**Required inputs:** Agreed architecture, named contract owner, curated entity IDs and provenance rules.

**Blockers / remaining gates (28 October 2026):** Shared schemas/fixtures exist; completion needs Python, web and native conformance evidence, not just schema publication.

- Model `ScenarioRevision`, `TrainingSession`, `FleetVehicle`, `RouteRevision`, `Disruption`, `Incident`, `Candidate`, `Charger`, `DispatcherCommand`, and `Event` with stable IDs.
- Represent session lifecycle, vehicle service state, and incident lifecycle explicitly; encode permitted transitions rather than inferring them from UI labels.
- Include scene/transform revision, simulation tick, event sequence, session epoch, route revision, and source provenance in applicable envelopes.
- Define full snapshot, event replay, command status, structured validation failures, and bounded error payloads for Python, TypeScript, and C++ consumers.
- Provide golden JSON examples and unknown-field/version behavior; distinguish historical simulation from actual recorded sensor data.

Output: versioned schemas, state transition tables, positive/negative fixtures, and a migration map from the existing single-trajectory contract.

Verification: both clients parse identical fixtures; invalid enum values, missing references, stale revisions, and incompatible major versions fail predictably.

## BE-M2-02: Build the deterministic five-shuttle session actor

**Dependencies:** [BE-M2-01](m2.md#be-m2-01-define-the-training-domain-and-versioned-contracts).

**Required inputs:** Seeded five-shuttle fixture, route loops and declared dwell/energy parameters.

**Implementation / remaining gates (28 October 2026):** The opt-in `scenario-m2-integrated-r1` now executes approved route replacement, incident holds, physical depot travel and shared charger allocation/release on one durable planar actor. Backend determinism and recovery are tested; rendered client agreement remains shared acceptance evidence.

- Introduce one authoritative actor per session with a fixed 50 ms logical step; use explicit seeded random state and stable entity iteration.
- Support route loops, stop dwell, depot/standby, blocked/awaiting-decision, and charging states for five shuttles across three route patterns.
- Advance all vehicles on the same clock; pause, resume, and reset are commands with recorded outcomes.
- Add bounded occupancy/headway checks and deterministic safe stopping for the curated road fixture; five shuttles must not pass through one another merely because their route progress is computed independently.
- Generate 10 Hz immutable presentation snapshots from committed state; clients interpolate between samples without changing backend state.
- Keep route search, JSON asset loading, filesystem work, and export creation outside the simulation step.

Output: headless runner, deterministic initial scenario fixture, state hashes, and a backend-owned fleet snapshot.

Verification: repeated runs with the same manifest, seed, and command ordering yield identical discrete transitions and documented numeric tolerances; connecting a second client never creates a second simulation loop.

records the verified headless actor, single-owner scheduler, immutable fan-out,
regressions and remaining live persistence/3D integration gates. This is not a

## BE-M2-03: Persist commands and recoverable state

**Dependencies:** [BE-M2-01](m2.md#be-m2-01-define-the-training-domain-and-versioned-contracts), [BE-M2-02](m2.md#be-m2-02-build-the-deterministic-five-shuttle-session-actor).

**Required inputs:** Runtime SQLite, migration policy and recoverable private actor state.

**Implementation / remaining gates (28 October 2026):** The integrated backend recovers approved routes, incident holds, depot progress, reservations and charging timers as a paused session with a new epoch. Queued inputs require reconfirmation and applied outcomes remain replayable. Paired-client recovery evidence remains a shared acceptance check.

- Add a runtime SQLite database with WAL, explicit schema migrations, transactional updates, and a bounded single-writer queue; retain the existing scene database as read-only.
- Deduplicate commands by authenticated actor, session, and idempotency key; record reason where required, payload hash, expected target-aggregate revision, acceptance status, and final result. A continuously advancing tick is not the revision precondition for every click.
- Persist acceptance before returning `QUEUED`; validate preconditions again when applying at a simulation boundary.
- Atomically persist the resulting revision, event sequence, and `APPLIED`/`REJECTED` command outcome before publishing visible state; do not report a queued action as applied.
- Persist a recoverable checkpoint and ordered inputs/events; introduce a new connection epoch on process recovery and expose previously active sessions as `PAUSED`. Unstarted `READY` sessions remain `READY` so pre-trip approval and Start remain available. Old queued approvals become `NEEDS_RECONFIRMATION` or expire unless explicitly safe and revalidated.

Output: migrations, command-status endpoint, event replay endpoint, checkpoint format, and documented restart behavior.

Verification: retry after lost acknowledgement, duplicate key with different payload, restart after acceptance, and crash before/after application commit each produce one durable outcome without silently executing twice.

Implementation handoff: [BE-M2-03 persistence](../milestone_status/M2/be-m2-03-status.md) documents the SQLite store, endpoints, checkpoint, and recovery behavior. The v2 fleet actor and authentication middleware are required for a live training session.

**Implementation / remaining gates (28 October 2026):** The integrated planar session now uses one obstruction identity and executes incident decisions, live battery forecasts, reachable depot travel, bay arrival, charging and port release. The complete-workflow baseline passed 77 checks over 4,004 ticks with zero dropped trace records; the current full backend suite passed 832 tests with 4 skips. Raw timings, command/event trace, source hashes and open risks are retained. See [collection, measured budget misses and verification](../session_creation.md#backend-instrumentation-and-evidence).

**Reporting update / remaining verification:** The collector now reports active real-time factor in per-minute windows and server-observed current/oldest committed-state age, as required by [the performance specification](../performance.md#2-p1-latency-gates). Pauses, recovery epochs, unknown restored sample ages and manual-clock exclusions are explicit. Scheduler profiling and forced-process-crash evidence are recorded below; production remediation and historical compute-cost validation on a locked reference remain open. The P0 runs do not supply the prescribed production warmup/trials, per-class sample counts or real reconnect measurements.

**Scheduler profiling:** Twelve controlled P0 cases identify Windows timer-wait granularity as the dominant measured source of the current wake-lateness miss. Actor-case p95 was 14.95 ms by default, 15.10 ms with a finer loop clock, and 1.76 ms with a temporary process-local 1 ms timer request. All requests were released. [Profiling evidence and BE-M2-06 remediation](../session_creation.md#scheduler-profiling) document the experiment, limitations and proposed running-actor timer guard. The production timer policy is not changed by this diagnostic.

**Process-crash recovery:** Twelve isolated real-process trials passed across uncommitted hold/charging ticks, durable acceptance before application, and committed application before its HTTP reply. Crash-to-verified-paused p95 was 1.78 seconds against the 5-second reference on this unlocked P0 machine. Checks verified zero lost committed outcomes, rollback of interrupted progress, new PAUSED epochs, retained private workflow state, reconfirmation of unapplied input, duplicate-safe retries and resumed physics. [The crash harness, evidence and limits](../session_creation.md#process-crash-recovery) distinguish this result from P1 and storage/power-loss acceptance.

**Shared acceptance: Pending.** Full BE-M2-06 acceptance still needs locked P1 content/hardware and real web/native command-to-paint probes. Historical compute-cost variation and the proposed scheduler remediation need validation on that reference; in-process backend timings do not establish client or P1 acceptance.

- Tag timings with command ID and session/epoch; measure durable acceptance, application, publication, route validation, queue depth, tick duration, and recovery.
- Lock the P1 scene and target hardware in the [performance specification](../performance.md).
- Target tick work p95 ≤10 ms / p99 ≤25 ms within a 50 ms step; acceptance p95 ≤150 ms / p99 ≤300 ms; same-client dispatch-to-visible application p95 ≤250 ms / p99 ≤500 ms on loopback.
- Target route validation p95 ≤300 ms / p99 ≤750 ms and cached reconnect p95 ≤2 s. Capture failures and missed ticks explicitly.
- Integrate web and native concurrently using the same IDs and command/event semantics; record differences as contract defects.

Output: benchmark harness, baseline report, integration trace, test result artifact, and an open-risk register.

## M2 exit gate

1. Either client can create the exercise, approve the detour, resolve the incident, make the charging choice, and inspect the provisional score/log; the peer sees the same committed result.
2. A lost connection and backend restart preserve command records, applied decisions, route revisions, and incident evidence; stale queued approvals require reconfirmation and cannot execute unexpectedly.
3. Invalid route/option approvals are rejected with actionable structured errors, and reliable events are recoverable even when snapshots are coalesced.
4. P1 measurements are reported against the proposed budgets; any miss has a measured cause and scheduled remediation before expansion.

Deferred to M3: full time-window/avoid-area editing, multi-incident scheduling, general charging plans and swaps, trainer authoring UI contracts, and completed assessment/report workflow.
