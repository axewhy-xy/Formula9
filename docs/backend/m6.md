# M6: Frozen release, deployment, and final acceptance

Task planning notes use the [dependency and blocker conventions](../milestones.md#task-dependencies-and-issue-creation). Dependencies name prerequisite artifacts; final paired evidence is a shared acceptance gate, not a reason to serialize client development.

3D extension (27 October 2026): existing tasks and handoffs are preserved. The added BE-M6-07 through BE-M6-09 tasks and additional exit criteria are cumulative; follow the [mandatory 3D contract](../three_d_simulation.md) and [3D performance/spatial gates](../performance.md#8-3d-workload-and-spatial-acceptance). New tasks remain planned until verified.

Status: planned. Depends on M5 feature freeze, performance gates, recovery evidence, and compatible web/native release candidates.

M6 delivers a reproducible training application with a reliable backend, documented limits, and reviewable evidence. New feature work requires rescoping a later release rather than bypassing acceptance.

## BE-M6-01: Produce a reproducible backend release

**Dependencies:** [BE-M5-06](m5.md#be-m5-06-freeze-contracts-and-publish-release-evidence).

**Required inputs:** Pinned Python/dependencies, supported deployment configuration and clean machine.

**Planned blockers / completion gates:** Release package must start headlessly with declared mandatory assets and no developer paths or internet content fetches; final spatial bundle comes from BE-M6-07.

- Pin supported Python and dependency versions and package the server, migrations, scenario manifests, and required static assets.
- Publish one supported startup path with explicit configuration for scene assets, runtime database, ports, allowed origins, and authentication mode.
- Start without a GPU, native executable, internet download, or optional recorded media; readiness reports which optional capabilities are available.
- Bind local development/package mode to loopback by default; shared LAN mode uses the documented authentication and transport configuration.
- Include build ID, schema version, scenario hashes, and diagnostic version information in support output and exported reports.

Output: backend release artifact, dependency lock, configuration reference, integrity manifest, and clean-machine installation procedure.

Verification: install and start on a clean supported machine using only the release package and documented prerequisites.

## BE-M6-02: Validate upgrade, rollback, and data recovery

**Dependencies:** [BE-M6-01](m6.md#be-m6-01-produce-a-reproducible-backend-release), [BE-M5-05](m5.md#be-m5-05-harden-access-storage-and-reports), [BE-M5-08](m5.md#be-m5-08-harden-scene-integrity-and-spatial-recovery).

**Required inputs:** Copied M5 records, verified backups and schema/code rollback boundaries.

**Planned blockers / completion gates:** Migration/restore must preserve command outcomes, scores and exact geometry lineage; unsupported combinations must stop explicitly rather than reinterpret attempts.

- Rehearse migration from the M5 supported runtime schema using a copy containing completed attempts, pending commands, and generated reports.
- Take and verify a backup before migration; preserve failure diagnostics and avoid partially migrated writable state.
- Document code/schema compatibility and rollback boundaries, including restoration from backup when a migration is not backward compatible.
- Restore a backup into an isolated deployment and verify session/event lineage, route decisions, charging plans, and rubric versions.
- Confirm scene asset replacement cannot silently reinterpret a saved exercise under a different geometry or transform.

Output: tested upgrade/rollback guide, migration logs, restored evidence manifest, and compatibility table.

Verification: restored debrief scores and command outcomes match the original records; unsupported schema/scene combinations stop with an actionable error.

## BE-M6-03: Complete integrated release acceptance

**Dependencies:** [BE-M6-01](m6.md#be-m6-01-produce-a-reproducible-backend-release), [BE-M6-02](m6.md#be-m6-02-validate-upgrade-rollback-and-data-recovery).

**Required inputs:** Frozen scenario/seed suite and matching packaged web/native builds.

**Planned blockers / completion gates:** Final acceptance needs every core workflow, permissions/conflicts/recovery and report identity on released artifacts; no developer database repair or hidden scripts.

- Execute the frozen exercise suite from both clients, including pre-trip edit, route rejection, incident response, wait/escalation, charging/swap, debrief, and export.
- Attach web and native to the same session and verify interleaved commands, duplicate retries, stale previews, conflict responses, and matching event cursors.
- Perform a cold start, planned reconnect, abrupt disconnect, backend restart, scenario reset, and exercise completion with the release packages.
- Verify every reference solution stays hidden until its configured stage and every non-approvable capability is represented consistently.
- Confirm reports contain the original scenario, scoring revision, assumptions, timing definitions, provenance, and all relevant decision outcomes.

Output: end-to-end acceptance report, client/server build manifest, evidence traces, and exported example results.

Verification: all mandatory scenarios pass without developer database edits, hidden reset scripts, or manually repaired reports.

## BE-M6-04: Re-run performance on the final packaged build

**Dependencies:** [BE-M6-01](m6.md#be-m6-01-produce-a-reproducible-backend-release), [BE-M5-01](m5.md#be-m5-01-establish-reproducible-performance-acceptance).

**Required inputs:** Frozen P1/P2 setup, working packaged workflows and both clients' paint probes.

**Planned blockers / completion gates:** Final P1 and four-hour soak must run on exact release packages with raw evidence; subsequent fixes require affected reruns. Coordinate spatial workload with BE-M6-08.

- Repeat P1 under the locked hardware and workload used at M5; package/startup changes are included in the measurement.
- Verify tick work p95 ≤10 ms / p99 ≤25 ms; durable command acceptance p95 ≤150 ms / p99 ≤300 ms.
- Verify same-client dispatch-to-visible application and fleet state age p95 ≤250 ms / p99 ≤500 ms at 1× under the specified loopback conditions.
- Verify route validation p95 ≤300 ms / p99 ≤750 ms; bounded candidate search p95 ≤1 s / p99 ≤2 s; cached reconnect p95 ≤2 s.
- Retest a representative P2 stress case and controlled network degradation; publish overload limits alongside P1 results.
- Complete a four-hour soak on the frozen packages, including repeated exercises, history/debrief inspection, previews, exports, reconnects, and resource-growth measurements.
- Publish raw timing data, sample counts, cold/warm state, failures, and environment manifest so the presentation can substantiate performance claims.

Output: final performance report, four-hour soak report, and reproducible measurement bundle.

Verification: release fixes cannot regress accepted budgets; any revised target is visible, justified by evidence, and agreed before final acceptance.

## BE-M6-05: Support instructor and trainee usability validation

**Dependencies:** [BE-M6-01](m6.md#be-m6-01-produce-a-reproducible-backend-release).

**Required inputs:** Working frozen clients, agreed observation script, participants and consent/retention policy.

**Planned blockers / completion gates:** Observed explanation/recovery failures need fixes and regression retests; lack of participants/evidence blocks usability sign-off, not package preparation.

- Run observed tasks that exercise backend explanations: invalid route, changed option, delayed shuttle, unavailable charger, and reconnect during a decision.
- Record completion, failed attempts, explanation comprehension, active decision time, and operational outcome using the frozen measurement definitions.
- Distinguish usability evidence from simulator validity and learning effectiveness; state participant counts and study limits.
- Fix misleading error details, missing evidence, contract mismatches, and incorrect outcomes discovered in these sessions.
- Preserve all assessment results used in the final presentation with anonymized labels and the consent/retention policy selected by the team.

Output: backend-related usability findings, issue resolutions, and anonymized example debrief artifacts.

Verification: users can understand why an action failed or changed without reading server logs; fixes pass affected regression and integration tests.

## Additional 3D exit criteria

- The packaged headless backend and both 3D clients reproduce the same pinned world and retained attempts on a clean supported setup.
- Spatial conformance, final 3D performance and four-hour recovery/soak evidence pass; missing mandatory geometry is release-blocking.
- New 3D task evidence and model/content guidance are included in the handover without rewriting earlier completion records.

## M6 exit gate

1. A reviewer installs the release, runs a complete exercise through either client, opens the debrief, and exports valid results using the documentation.
2. Both clients agree on committed fleet, incident, route, charging, and score state, including after restart/reconnect.
3. Final measured P1 budgets, the four-hour soak, recovery tests, migration checks, and mandatory scenario results pass on the packaged build.
4. Claims in the presentation are supported by recorded evidence and clearly distinguish measured behavior from proposed future capabilities.

Deferred work is recorded for a future release. Optional perception, broader manoeuvre physics, distributed deployment, and larger fleet optimization do not enter M6 without restarting the affected acceptance gates.
