## BE-M5-01: Establish reproducible performance acceptance

**Dependencies:** [BE-M4-06](m4.md#be-m4-06-validate-depth-without-latency-regression).

**Required inputs:** Frozen P1/P2 datasets, hardware/runtime inventory, LAN conditions and both clients' probes.

**Planned blockers / completion gates:** Final acceptance needs exact workloads and raw samples. Mandatory P1 and P2 correctness/recovery/resource failures block release; indicative P2 speed misses require supported-capacity disclosure.

- Run P1 on the locked hardware/OS/runtime versions with five shuttles, three routes, two chargers, 5,000 directed edges, and two paired clients at 1×.
- Separate cold scene load, warm interaction, steady shift, burst editing, incident concurrency, export activity, and cached reconnect.
- Record acceptance-to-application and client dispatch-to-visible application separately; report server processing, queueing, persistence, publication, network, and client delay where instrumented.
- Report tick work, state age, command results, route validation/candidates, memory, CPU, queue depths, WAL size, and deadline misses with raw measurement artifacts.
- Validate loopback and a controlled LAN with RTT ≤40 ms; the permitted additional 50 ms applies only to command-to-visible latency and fleet state age. All other budgets remain unchanged.
- Run P2 independently with 50 shuttles, 10,000 directed edges, and ten subscribers. Correctness, recovery, and bounded resources are mandatory; compare speed with the indicative P2 targets and report measured supported capacity and degradation separately from P1.

Output: reproducible benchmark command, dataset hashes, environment manifest, percentile report, and flame/profile evidence for any miss.

Verification: mandatory P1 budgets and P2 correctness, recovery, and bounded-resource checks in [performance.md](../performance.md) pass under their specified workloads or become explicit release-blocking defects with measured causes. Indicative P2 speed misses require a documented supported-capacity limit, not a false claim of meeting the target.

## BE-M5-02: Remove measured contention and cap work

**Dependencies:** [BE-M5-01](m5.md#be-m5-01-establish-reproducible-performance-acceptance).

**Required inputs:** Measured contention profiles and declared queue/cache/admission limits.

**Planned blockers / completion gates:** Optimization requires reproducible before/after evidence; weakening durability or dropping reliable events to meet timings blocks acceptance.

- Profile actor work, serialization, SQLite transactions, worker transfer, graph search, and GC before selecting optimizations.
- Serialize immutable fleet snapshots once per publication and share encoded payloads across subscribers.
- Use revision-keyed graph/route caches with memory budgets, cancellation-aware preview jobs, and admission control for expensive work.
- Keep a bounded durable writer and bounded process pool; report queue saturation with retryable errors before acceptance when work cannot be admitted.
- Ensure CPU-heavy route/branch/export activity cannot block the API event loop or the authoritative session actor.
- If optimizing persistence batching, preserve the documented durability boundary: never acknowledge acceptance or publish applied state before its required commit.

Output: profiling-driven changes, resource limits, queue policy, and before/after measurements under identical conditions.

Verification: saturation never produces unbounded memory, invisible accepted commands, lost reliable events, or false successful approvals.

## BE-M5-03: Exercise crash and restart semantics

**Dependencies:** [BE-M2-03](m2.md#be-m2-03-persist-commands-and-recoverable-state), [BE-M3-09](m3.md#be-m3-09-persist-and-replay-the-complete-3d-state).

**Required inputs:** Full M4 command paths, crash injection points and copied recoverable attempts.

**Planned blockers / completion gates:** Every acceptance/application/commit crash boundary must retain one durable outcome, paused recovery and explicit reconfirmation; data loss or duplicate effects block release.

- Inject failure after durable acceptance, during command application, before/after commit, during snapshot write, and during export publication.
- Recover the latest valid checkpoint plus ordered durable records; verify checksums/versions and fail clearly on incompatible or corrupted state.
- Advance the session epoch, restore final command outcomes, and recover to `PAUSED`. Old `QUEUED` approvals become `NEEDS_RECONFIRMATION` or expire unless explicitly safe and revalidated; a retry of an already `APPLIED` command returns its original outcome.
- Test duplicate and out-of-order requests, response loss, abrupt client disconnect, server shutdown, and reconnect beyond retained event history.
- Use bounded shutdown: stop new acceptance, commit or preserve accepted work, close subscriptions with recovery information, and report incomplete jobs accurately.

Output: fault-injection suite, restart matrix, recovery runbook, and captured recovery traces.

Verification: no committed decision disappears, no command is applied twice, no client accepts an obsolete epoch, and a full resynchronization converges on authoritative state.

## BE-M5-04: Test storage, network, and worker failure boundaries

**Dependencies:** [BE-M3-06](m3.md#be-m3-06-maintain-latency-and-reliable-collaboration), [BE-M3-05](m3.md#be-m3-05-persist-debrief-score-explanations-and-exports).

**Required inputs:** Storage/network/worker fault harness and bounded readiness/error policy.

**Planned blockers / completion gates:** Disk/WAL/worker/slow-subscriber faults must preserve committed state and isolate optional work; uncommitted success or uncontrolled failure blocks release.

- Simulate disk-full/read-only storage, WAL contention, busy timeout, missing scene asset, worker crash/timeout, and unavailable recorded media.
- Refuse new durable commands cleanly if persistence is unavailable; preserve/recover the last committed state and do not emit uncommitted progress as successful state.
- Restart failed workers within bounded policy and cancel jobs whose session/revision is no longer valid.
- Coalesce only fleet snapshots; replay or resynchronize reliable events for slow subscribers, and close persistently unhealthy connections with explicit recovery guidance.
- Apply request/body limits, timeout policies, import/export size limits, and per-role/session rate limits.

Output: failure behavior table, operational health/readiness endpoints, structured diagnostic codes, and isolation test artifacts.

Verification: exports or optional media can fail without stopping the exercise; persistence failure produces a visible controlled session state rather than silent data loss.

## BE-M5-05: Harden access, storage, and reports

**Dependencies:** [BE-M3-04](m3.md#be-m3-04-add-minimum-trainer-authoring-and-assignment), [BE-M3-05](m3.md#be-m3-05-persist-debrief-score-explanations-and-exports), [BE-M4-01](m4.md#be-m4-01-extend-scenario-authoring-with-validated-dependencies), [BE-M4-05](m4.md#be-m4-05-explain-assessment-patterns-across-attempts).

**Required inputs:** Access/retention policy, copied databases, migration plan and deployment settings.

**Planned blockers / completion gates:** Authorization, safe imports/exports and restore integrity require evidence; missing retained scene/rubric lineage or cross-attempt disclosure blocks completion.

- Verify trainer/trainee/session authorization on every mutation, replay, report, and reference-answer endpoint.
- Validate file paths, imported manifests, uploaded metadata, filenames, and log text; avoid path traversal and spreadsheet formula execution.
- Configure allowed origins and WebSocket access; document local-only default and authenticated/TLS access for shared LAN deployment.
- Implement backup/restore and schema migration rehearsals on a copied runtime database, with integrity checks and rollback guidance.
- Apply retention to temporary previews/exports and completed attempts without deleting scenario evidence still referenced by retained results.

Output: threat-focused tests, deployment settings, retention policy, backup/restore evidence, and migration procedure.

Verification: unauthorized requests cannot mutate or read another attempt; restored results retain event lineage, hashes, and the exact scoring revision.

**Planned blockers / completion gates:** Required geometry failures must prevent readiness/approval; restore must recover exact scene/proxy revisions without surprise commands or stale job installation.

Output: scene integrity/fault matrix, bounded import/asset checks, recovery traces and geometry-aware backup/retention procedure.

Verification: corrupt operational data cannot produce an approved route or ready session; optional detail failure stays isolated, and restored attempts recover the same geometry/decisions without surprise approvals.

## Additional 3D exit criteria

- All added spatial profiling/integrity/conformance tasks pass on the same scene package used by the clients.
- Two-hour endurance and P2 fault tests include the real 3D workload, with no geometry substitution, unbounded indexes or incorrect spatial approvals.
- Mandatory capability/schema/content dependencies are frozen for the 3D release.

## M5 exit gate

1. P1 budgets, invariant checks, and the two-hour soak pass with raw evidence. P2 correctness, recovery, and bounded-resource checks pass; speed results, supported capacity, and overload behavior are documented separately.
2. Crash/retry/reconnect tests preserve durable outcomes and converge both clients on the same session.
3. Access control, backup/restore, migration, resource bounds, and report integrity have reproducible evidence.
4. Both clients complete every mandatory exercise with the frozen contract; only release fixes proceed into M6.
